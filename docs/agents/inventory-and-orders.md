# Inventory, purchase orders, receiving, calibration

Read before touching `Item`, `WarehouseStock`, `MachineStock`, `src/actions/orders.ts`, `OrderManagerUI`, `src/lib/order-entry.ts`, `src/lib/packaging.ts`, `src/lib/receipt-totals.ts`, or the calibration / cost-correction modals. Also read the skills `.agents/skills/vms-accounting-wac` and `vms-audit-trail`.

## Core model

- **WAC** (weighted-average cost) is recomputed when a PO is received. Supplier shortages stack into `WarehouseStock.pending_deficit`, never into negative inventory. `Item.cost` = running WAC; `last_purchase_cost` = latest price paid.
- WAC flows into P&L through `RefillLog.cost_at_refill` snapshots and live shrinkage. A PO entered at the wrong `costPerUnit` silently corrupts it. That's why stock and cost corrections go through calibration (below), never through fake POs.
- Three price tiers on `Item` (`price_standard`/`hospital`/`hotel`). `Machine.tier` selects which one applies at refill.
- `Item.default_assignment_qty` is the **driver batch**: the `+N` button in `DriverStockManager` next to the `+1` stepper (one batch per click, hidden when 0; editable in `/admin/manage` → Items, capped 0–100 server-side in `updateItem`). It is **not** the supplier carton (`Item.pieces_per_box` × `Item.packets_per_carton`, see [Cartons, packets and pieces](#cartons-packets-and-pieces)). The two differ (MOVENPICK: carton of 10, batch of 3). It must never leak into refill quantities.
- Soft delete: drivers/machines/items/warehouses flip `isActive`. `deleteDriver` (`inventory.ts`) **hard-deletes** a driver with zero history (no `RefillLog`/`ReturnVerification`/`StockAssignment`/`Dispatch`; `DriverStock` cascades) and otherwise soft-deletes, to keep the denormalized `driverId` audit trail. On a P2003 FK error it falls back to soft-delete. `/super/admins` deliberately shows inactive drivers with an "Inactive" badge; every other driver list hides them.

## Purchase orders — drafting

The admin keys a ~60-line supplier order from paper. The rules are pure functions in `src/lib/order-entry.ts` (tested in `tests/lib/order-entry.test.ts`; `OrderManagerUI` only renders them; the flow is pinned by `tests/components/OrderManagerUI.test.tsx`):

- **A line is typed in cartons** and stores pieces (`quantityRequested`; the server never sees a unit). A per-line select switches to pieces for an odd amount. There is deliberately **no packets unit**: see the packets rule under [Cartons, packets and pieces](#cartons-packets-and-pieces). The unit shown is the one the admin picked while the quantity is a whole number of it, otherwise the biggest unit that divides it exactly (`lineUnit`), so an inherited 700 SIPP GREEN shows as "700 pcs" and is never silently rounded. Switching unit rounds **up** to whole units (`withUnit`). The typed unit is dropped before `createPurchaseOrder`.
- **A new line starts at what was last ordered of that item, rounded up to whole cartons** (`startingQuantity` over `lastOrderedByItem`, newest non-cancelled order), falling back to one carton, or 1 piece for a loose item. It is always whole cartons so the line opens in cartons: an unrounded 700 opened in a smaller unit and the admin's "5" didn't mean 5 cartons (found in the browser). The line shows "Last time: … on <date>" and what's in the warehouse, both in cartons. (It was once a hard-coded 1, then the driver batch, then one box.)
- **`−`/`+` step one of the line's unit, and `−` refuses rather than clamps** below one unit (`stepLine`).
- **Bulk starting points only ever append** (`mergeOrderLines`): "Repeat last order" (per destination warehouse; uses `quantityRequested` so a short shipment doesn't shrink the next order; drops *and counts* deactivated items), "Order these again" in the history modal, and "Add N shorted items" (`pending_deficit` rounded up to whole cartons). None may overwrite a quantity the admin typed, and none rounds: bulk lines keep their exact pieces and show in whichever unit divides them.
- **Keyboard loop: name → Enter → Enter.** Enter in the search adds the highlighted match and lands in the new line's quantity box with the number *selected*. Enter there accepts it and returns to search; typing replaces it. A mouse click instead keeps focus in the search box with the list open (`onMouseDown` `preventDefault`), so several items can be picked in a row. Searching for an item already on the order jumps to its line.
- **Lines render newest-first** so the line just added sits under the search box. State stays in insertion order, so the submitted/printed PO order is unchanged.
- **The draft is persisted to `localStorage` (`vms:po-draft`)**, restored after mount and cleared on submit. Changing the destination warehouse does not wipe the lines.
- Only `isActive` items are orderable. The unfiltered `items` prop is kept because pending/history rows still look up inactive ones. `createPurchaseOrder` rejects empty orders, non-integer or < 1 quantities, and duplicate items server-side.
- The Create Order tab shows an **Estimated Order Value** (unit cost = `Item.cost`, the WAC snapshot `createPurchaseOrder` locks per line).

## Purchase orders — receiving

A pending order card lists its lines in cartons (first 6, then "Show all N items") and has **Copy order**: `orderAsText` puts a supplier-ready message on the clipboard (PO number, destination, one line per item in cartons) for WhatsApp or email. Order History marks completed orders where a line arrived short ("2 items arrived short"); the printed PO shows cartons first, pieces underneath.

The Pending Receipts tab shows a live **Receipt Summary** (line count, units, subtotal, 15% VAT, grand total; math in `src/lib/receipt-totals.ts`, tested against a real supplier invoice in `tests/lib/receipt-totals.test.ts`) so the receiver can match the paper tax invoice, and the confirm dialog restates the totals. Amounts are entered **excluding VAT**, so the subtotal lines up with the invoice's pre-VAT "Total Amount". Suppliers round VAT per line, so the grand total may drift a few halalas from `subtotal × 1.15`. That still counts as a match.

### Cartons, packets and pieces

The client's rule: stock **arrives in cartons but is counted and dispatched in pieces**, and a receiver must be able to say whether *this* delivery's carton held 24 or 20. So cartons exist only at the warehouse door (ordering and receiving), and every stock table stays in pieces. The rules are pure functions in **`src/lib/packaging.ts`** (tested in `tests/lib/packaging.test.ts`).

- **Up to three levels, carton → packet → piece**, the way the client writes his pack codes (`8*20*5GM` = a carton of 8 packets of 20). **`Item.pieces_per_box`** is the innermost unit: the packet, or the carton itself when there are no packets (AQUAFINA: a carton of 40). **`Item.packets_per_carton`** is the level above it (null = the carton holds pieces directly). `levelsOf()` normalises the pair; a carton is `perPacket × packetsPerCarton` pieces. The packet level was added on 2026-09-22 after report `R-FPWZK` ("1 carton × 8 packets × 20 pieces = 160, the program does 1 carton × packet + piece"): with one level, the stored "box" was the client's packet for 26 items and his carton was stored nowhere.
- **`piece_size` + `piece_size_unit`** (`g`/`kg`/`ml`/`L`) are display only: "Carton of 8 packets × 20 × 5 g". Edit all four in Manage → Items (`updateItem`'s optional `packaging` arg; omitted means *leave alone*, so no caller blanks them by accident) or in the PO "New Item" modal (`createQuickItem`), both through `ItemPackagingFields`: the second field's label follows the first ("Pieces per packet" / "Pieces per carton"), the multiplication is written out under them, and when the pack code can be read without guessing (`packetsPerCartonFromPackCode`) a "Use 8" button fills packets in one tap. A cleared size is stored as **null, never 0**, and a carton of one packet as null. `parsePackaging` rejects packets without a packet size of 2+. `Item.bulk_format` stays as the free-text "Pack code", shown only where no structured packaging exists.
- **Packets are a size, never a count.** "Packets" appears only in the carton's definition ("1 carton = 8 packets × 20 = 160 pcs", `describeCartonSum`) and in the size fields. Every quantity — order lines, receiving, the warehouse table, Copy order, the print — is **cartons + loose pieces** (`splitCount`, `describeCount`). An earlier version of this branch also had a loose-packets count on the receiving line; the user pulled it because the client's admin reads little English and "Packets" next to "Packets per carton" was one word with two meanings on one line.
- **Receiving asks for cartons + loose pieces, at a price per carton** (three boxes; loose pieces is where a part-carton goes). Pieces = `piecesFromCount` (cartons count only when the item has one, matching the fields on screen); cost per piece = carton price ÷ carton size. Asking for a carton price is the point: the invoice prints one, and the old per-piece field was being fed carton prices. **AQUAFINA WATER (a 2 SAR bottle) is costed at 31 SAR in production** for exactly that reason, and it flowed into WAC. A line whose piece cost exceeds its standard price shows a warning. Everything is pre-filled (the order split into cartons, the carton price from `last_purchase_cost`), so an as-ordered delivery is a price check. Only cartons and price are in the Enter path.
- **The carton size is a sentence ("1 carton = 8 packets × 20 = 160 pcs") until "Different this time?"** opens the two size inputs for this delivery only; selling prices are likewise one sentence until "Change selling prices". A changed size keeps an orange "Usually …" note.
- **`PurchaseOrderItem` records how a line was counted** (`recordCount`): `boxesReceived` full innermost packs of `piecesPerBox` (the packets inside the cartons, or the cartons themselves), and, with packets, `cartonsReceived` of `packetsPerCarton` (all null on lines received before this and on loose items). The columns could hold loose packets (`boxesReceived > cartonsReceived × packetsPerCarton`) and the server accepts that, but the screen never sends it. `quantityReceived` stays the source of truth; `checkReceivedBoxes` rejects a breakdown worth more than was received, and each pair must come both-or-neither. Receiving overwrites **`PurchaseOrderItem.costPerUnit` with the per-piece cost actually paid**. Rows received before box counting still hold the order-time estimate.
- **Receiving never changes the item's usual sizes.** A one-off 20-carton shouldn't silently change the default for the next order; the admin edits the item instead.
- The warehouse table shows each quantity in cartons underneath ("21 cartons + 24 pcs", `describeCount`). Recounts (calibration) are still typed in pieces. The driver-stock `+N` keeps the driver batch.
- **Backfill of `pieces_per_box`:** `npm run db:seed-packaging:{dev,prod}` → `scripts/seed-item-packaging.ts` + `prisma/seed-data-templates/Item_Packaging.csv` (seed contract in [build-and-deploy.md](build-and-deploy.md#seeding)), **fill-only** unless `--overwrite`. How the CSV was read (its Source column cites each row): the client's pack code (`Item.bulk_format`) gives the piece size and the candidate counts, and the driver batch or the morning-load sheet's `(24X1)` picks which count is the packet, so `32*12*36GM` with a batch of 12 is packets of 12 × 36 g. A bare count is the carton (`30*240ML`, `10X1`, `12`). An item with no pack code takes its driver batch. **Production was filled from it on 2026-09-19** (fill-only, so sizes already typed in the app were kept): 63 of 64 active items have a size, 45 a piece size. **Deliberately left empty:** SNICKERS (sheet and batch say 24, the pack code `12*20*45GM` says 20: the client's question), Pringles' size (`30/40G`), and every size no pack code states. **Least certain:** the four cakes (45, from `45X1`; batch 3), `LIPTON PEACH ZRO` (6, batch only), `landessa` (12, bare pack code).
- **Backfill of `packets_per_carton`:** the other count of a three-count pack code, via `packetsPerCartonFromPackCode` (fill-only: `UPDATE … WHERE packets_per_carton IS NULL`, with the values generated by running that same function over a dump of the items, so the backfill can't disagree with the app's rule). It fills 25 production items (all 26 three-count codes except SNICKERS, which has no packet size to anchor on). The large ones (BISKREM 32 × 12, KITKAT 18 × 36, BOUNTY 12 × 24, OREO 12 × 12) could be cartons per case rather than packets per carton: **the client should confirm them**.

### `completePurchaseOrder` is set-based

It used to run ~8 sequential queries per line inside the transaction and P2028'd on a real SAR 124k invoice (the general rule is in [driver-stock.md](driver-stock.md#batched-transactions)). Three consequences to preserve:

1. The prior-quantity reads across warehouse + machines + driver bags are **3 `groupBy`s before the tx**, not 3 aggregates per line, so WAC is blended against a snapshot taken just outside the transaction.
2. Two PO lines pointing at the same `Item` are **merged** first. Blending `(q1@c1)` then `(q2@c2)` equals one lot of `Σq @ Σ(q·c)/Σq`, and `UPDATE…FROM VALUES` is undefined for duplicate join rows.
3. `pending_deficit` is written raw (negative on an overage, which pays down an older shortage) and then **clamped to 0 by a follow-up `UPDATE`**. `ON CONFLICT DO UPDATE` can see `EXCLUDED` and the target row but not the `VALUES` alias, so one expression can't cover both `max(0, change)` and `max(0, existing + change)`.

The status flip is a guarded `updateMany` (`status: { not: 'COMPLETED' }`) as the transaction's **first** statement. It locks the PO row, so two receivers can't both apply stock.

## Warehouse calibration and cost correction

Correct warehouse stock/cost **without fake POs**. Both actions are in `src/actions/inventory.ts` and write `InventoryAdjustment` + `SystemAuditLog` **inside the tx**:

- `calibrateWarehouseStock(warehouseId, items[{itemId, physicalCount, foundUnitCost?}], note?)`: recount to an absolute quantity (`requireAdmin`). WAC is left unchanged for shortages and for found units valued at current WAC. A `foundUnitCost` re-blends WAC via `computeWeightedCost` (same warehouse + machines + driver bags aggregation as `completePurchaseOrder`). It never writes a `RefillLog`, because warehouse stock leaving is not a sale.
- `correctItemCost(itemId, correctedCost, note)`: direct WAC revaluation (`requireSuperAdmin`). It sets `Item.cost` and **never** rewrites frozen `RefillLog` history (post a correcting entry; don't edit the ledger).

UI: "Calibrate Stock" / "Correct Cost" on `/admin/warehouse` (`WarehouseAuditModal`, `CostCorrectionModal`). Correct Cost is super-admin-only (the page passes `isSuperAdmin`). Detection heuristic for bad costs: `cost > price_standard` (`scripts/find-suspect-costs.ts`).

### Machine calibration

`/admin/machine-stock` has a **sibling** "Calibrate Stock" button (`MachineInventoryTable` → `MachineAuditModal` → `reconcileMachineAudit`) that shares the warehouse modal's chrome and copy **by design** (same title pattern, explainer, columns, badges and confirm flow). Keep the two modals visually in sync, but **do not flatten the semantics**. A machine **shortage IS a sale** (booked as `RefillLog` revenue + COGS, since product leaves a machine by being vended). A warehouse shortage is neutral.

The explainer is `src/components/CalibrationLegend.tsx`: two colour-coded outcome cards (shortage / surplus) plus one optional caveat line. The **structure** is shared, so the pair stays in sync automatically, but every **string** is a prop, so neither modal can inherit the other's financial claim. Card headings reuse the row badges' words ("Shortage"/"Found" for the warehouse, "Missing"/"Surplus" for the machine). Colours are the `accent-pink`/`accent-green` tokens.

Both modals nest `ConfirmModal`; see the stacking rule in [ui-and-mobile.md](ui-and-mobile.md#modals).
